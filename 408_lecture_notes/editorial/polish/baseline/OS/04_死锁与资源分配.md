# 死锁：从资源分配状态判断能否继续 {#os-ch4}

进程因为没有资源而等待，并不一定发生死锁。必须继续追问：谁持有它所需的资源，持有者能否完成并归还，归还又依赖谁。本章把这种追踪分别用于死锁条件、资源分配图、安全检查和死锁检测。

除特别说明，讨论的是可重复使用的资源：每类可以有多个同类实例，资源只能在释放后再次分配；进程请求后若不能满足便等待，正常完成会归还已持资源。分析安全性还假定进程声明的最大需求可信，不超过系统允许的资源总量，并能在获得所需资源后有限完成。

## 死锁、饥饿和不安全状态 {#os-4-1}

**死锁**指一组进程中，每个进程都在等待只能由组内进程引起的事件（也可能是自身尚未执行的释放动作），因而这一组无法自行推进。最小的双资源例子是：P 持有 A 等 B，Q 持有 B 等 A；没有进程能到达释放步骤。

**饥饿**指某个进程长期得不到所需服务，而其他进程仍可能持续前进。例如读者不断加入，使写者一直拿不到写权限。**死循环**是执行路径自身不能结束，进程可能仍持续占用 CPU，不必等待其他进程。三者的机制不同，处理方法也不同。

### 四个必要条件是同时约束

| 条件 | 本章资源模型中的含义 | 怎样在状态中识别 |
| --- | --- | --- |
| 互斥 | 某类实例同一时刻只能给一个进程使用 | 资源不可被两个申请者同时使用 |
| 占有并等待 | 保持已有资源，同时等待新增资源 | 一个进程既有分配边，又有请求边 |
| 不可剥夺 | 未用完的资源不能被系统任意收回 | 只能由持有者按规则释放 |
| 循环等待 | 存在首尾相接的资源等待链 | P 等 Q，Q 又直接或间接等 P |

发生这类资源死锁时，四项同时成立；只满足其中一项或几项不能推出死锁。“四项必要条件都允许存在”也不等于任何时刻都已经死锁，还要检查实际持有与等待状态。单进程再次请求一个自己已经持有且不可重入的锁，也可能自我阻塞，不能把“死锁至少要两个进程”当作适用于所有锁语义的结论。

### 资源分配图中的环什么时候足够

进程用圆表示，资源类型用方框表示，框内点表示实例。$P_i\to R_j$ 是请求边，$R_j\to P_i$ 是一个实例的分配边。没有有向环，可排除这种资源等待死锁；有环时，若环中相关资源类型均只有一个实例，则可判定死锁。

若资源类型有多个实例，环只说明可能死锁。例如 P 持有 A 的一个实例、等待 B，Q 持有 B、等待 A，但 A 还有一个空闲实例，Q 取得它并完成后就能释放 B。图中已有等待环，却仍有解开它的执行通路。此时必须结合实例数化简或执行检测算法。

### 安全状态问的是“能否保证全部完成”

**安全序列**是进程的一种次序，使每个进程在轮到它时，现有可用资源加上此前已完成进程释放的资源，足以满足它尚需的最大资源量。存在至少一个安全序列，称当前状态安全。

安全不是说系统实际上只能按这一序列运行；该序列是可完成性的证据。**不安全**表示无法在最大需求假设下给出这样的保证，不代表此刻已经死锁。进程可能还没提出全部需求，也可能实际少用资源或提前释放。死锁状态必不安全；不安全状态可能在以后的某种申请序列中发展成死锁。

## 死锁预防：在规则中破坏一个条件 {#os-4-2}

**预防**是在分配规则上使至少一个必要条件不能成立，不必等到具体死锁已经出现。

让可共享的资源按共享方式使用，可以去掉相应的互斥条件；但打印机输出、独占锁等具有不可共享的语义，不能为了避免死锁而取消必要保护。一次性申请运行所需的全部资源，全部满足才开始，可以破坏占有并等待，但会降低利用率，并要求提前知道需求。申请失败时先释放已有资源再重试，也是针对保持关系的办法。

对可保存、恢复状态的资源，可以在适当时机剥夺并回滚，例如某些处理器或存储资源；正在打印到纸张上的半份输出却不能简单撤回。对所有资源规定统一编号，只允许按严格递增次序申请，可以破坏循环等待：若有环，沿环的资源编号必须不断增大又回到起点，无法成立。所有进程各自“先拿左边再拿右边”并不保证全局编号递增。

预防可能限制请求方式并造成资源闲置。**避免**则保留更多请求自由，在每次拟分配时检查结果能否仍安全。二者都在实际进入死锁前采取措施，但依据不同。

### 例 4-1　避免与检测需要的信息不同 {#os-ex4-1}

【2015】 若系统 S1 采用死锁避免方法，S2 采用死锁检测方法。下列叙述中，正确的是（　）。

Ⅰ. S1 会限制用户申请资源的顺序，而 S2 不会

Ⅱ. S1 需要进程运行所需的资源总量信息，而 S2 不需要

Ⅲ. S1 不会给可能导致死锁的进程分配资源，而 S2 会

A. 仅Ⅰ、Ⅱ　　B. 仅Ⅱ、Ⅲ　　C. 仅Ⅰ、Ⅲ　　D. Ⅰ、Ⅱ、Ⅲ

**解析。** 银行家式避免根据最大需求和当前状态决定批准或推迟，并非规定所有进程必须按统一资源顺序申请，Ⅰ混入了预防中的排序法。避免要判断未来最大需求是否仍可满足；检测根据当前已分配与当前等待请求判断，不要求事先掌握全过程最大需求。检测允许某些分配以后导致死锁，再检测和解除。因此Ⅱ、Ⅲ正确，答案为 **B**。

## 银行家算法：可用不等于可以批准 {#os-4-3}

设有 $n$ 个进程、$m$ 类资源。向量按同一资源次序排列，各分量逐项比较，不能用向量元素之和代替比较。

| 名称 | 含义 |
| --- | --- |
| `Available[j]` | 第 j 类当前未分配的实例数 |
| `Max[i][j]` | 进程 i 声明的第 j 类最大需求 |
| `Allocation[i][j]` | 进程 i 已持有的实例数 |
| `Need[i][j]` | 进程 i 尚可能需要的最大数量，等于 `Max-Allocation` |

### 安全性检查中的 Work 为什么要加 Allocation

先复制 `Work=Available`，所有 `Finish=false`。反复寻找未完成且 `Need[i] <= Work` 的进程：假定给足它的剩余需求，它完成后会归还所有资源，净效果是 `Work += Allocation[i]`，并标记完成。若最终所有进程都能标记，安全；若再无可选者但仍有未完成者，不安全。

之所以只加原 `Allocation`，是因为假借给它的 `Need` 已从 Work 暂时付出，又在完成时归还，二者抵消。把 `Max` 直接加到 Work，会凭空增加资源；把 Work 逐步减到负数再说“以后会归还”，则跳过了本算法的可完成前提。

```text
Work = Available
Finish[0..n-1] = false
while 存在 i: !Finish[i] 且 Need[i] <= Work:
    Work = Work + Allocation[i]
    Finish[i] = true
若全部 Finish 为真，则安全；否则不安全
```

### 例 4-2　能先完成两人，仍然可能不安全 {#os-ex4-2}

【2011】 某时刻进程的资源使用情况如下表所示，可用资源向量为 $(0,2,1)$。

| 进程 | 已分配 $(R_1,R_2,R_3)$ | 尚需分配 $(R_1,R_2,R_3)$ |
| --- | --- | --- |
| P1 | (2,0,0) | (0,0,1) |
| P2 | (1,2,0) | (1,3,2) |
| P3 | (0,1,1) | (1,3,1) |
| P4 | (0,0,1) | (2,0,0) |

此时的安全序列是（　）。

A. P1、P2、P3、P4　　B. P1、P3、P2、P4

C. P1、P4、P3、P2　　D. 不存在

**解析。** 初始只有 P1 的 Need 不超过 Work。假定 P1 完成，Work 从 $(0,2,1)$ 变为 $(2,2,1)$。此时 P2、P3 均需要 3 个 $R_2$，只有 2 个，不能选；P4 可以完成，释放 $(0,0,1)$，Work 变为 $(2,2,2)$。

| 已假定完成 | Work | 下一步 |
| --- | --- | --- |
| 无 | (0,2,1) | 只能选 P1 |
| P1 | (2,2,1) | 只能再选 P4 |
| P1、P4 | (2,2,2) | P2、P3 均差一个 $R_2$，停止 |

没有覆盖所有进程的安全序列，答案为 **D**。C 的前两步合法，不代表整条序列合法；不能因为“已释放了不少资源”就略过逐类比较。本题没有给出每个进程此刻实际阻塞的请求，所以不据此宣称已经死锁。

### 例 4-3　把每个候选可用向量独立试一遍 {#os-ex4-3}

〖2.4-026〗 系统有三类资源 A、B、C 和五个进程，某时刻分配如下。若系统安全，则可用资源向量 $(x,y,z)$ 可能是哪些？

| 进程 | Allocation | Max |
| --- | --- | --- |
| P0 | (0,0,3) | (0,0,4) |
| P1 | (1,0,0) | (1,7,5) |
| P2 | (1,3,5) | (2,3,5) |
| P3 | (0,0,2) | (0,6,4) |
| P4 | (0,0,1) | (0,6,5) |

Ⅰ. (1,4,0)　Ⅱ. (0,6,2)　Ⅲ. (1,1,1)　Ⅳ. (0,4,7)

A. Ⅰ、Ⅱ、Ⅳ　　B. Ⅰ、Ⅱ　　C. 仅Ⅰ　　D. Ⅰ、Ⅲ

**解析。** 五个 Need 依次为 $(0,0,1)$、$(0,7,5)$、$(1,0,0)$、$(0,6,2)$、$(0,6,4)$。每个候选都从初态重新检查，不能沿用上一候选已经“释放”的资源。

Ⅰ中，P2 可先完成，Work 从 $(1,4,0)$ 增至 $(2,7,5)$，其余四个的 Need 都能满足，因此安全。Ⅱ中可先完成 P0、P3、P4，Work 最多达到 $(0,6,8)$；P2 差 A，P1 差 B，不能继续。Ⅲ中可先完成 P0、P2，Work 到 $(2,4,9)$，其他三个都至少需要 6 个 B，仍只有 4 个。Ⅳ中只能先完成 P0，Work 到 $(0,4,10)$ 后停止。故仅Ⅰ安全，答案为 **C**。

这道题的两种不安全原因不同：Ⅱ即使 C 很多，A、B 的短缺仍不能互相抵补；Ⅲ也不能靠增加 A、C 弥补 B 的不足。

### 新请求的三个关口

进程 $i$ 请求向量 `Request`，依次检查：

1. `Request <= Need[i]`。否则超出原先声明的最大需求，不是正常等待问题。
2. `Request <= Available`。否则当前没有足够实例，应等待，不能先分成负数。
3. 试分配：Available 减 Request，Allocation 加 Request，Need 减 Request；对新状态做完整安全检查。安全才提交，否则恢复原表并推迟请求。

第二步只说明“拿得出来”，第三步才说明“拿出以后仍有完成保证”。下列最小反例用于区分两步：**原创机制示例**，一类资源共 4 个，P、Q 分别最多要 4、3 个，已各得 1 个，可用 2 个。当前可先让 Q 取得剩余 2 个、完成后释放，再供 P，故安全。若再给 P 1 个，可用只剩 1，P 尚需 2，Q 也尚需 2，变为不安全。请求既不超最大需求，也不超现存量，仍应拒绝立即分配。

### 总资源界限不能代替银行家逐态检查

若 $n$ 个进程每人最多需要 $k$ 个同类不可剥夺资源，为了在**任意分配顺序**下都保证至少有一个人能够拿齐，可用最坏状态论证：每人都持有 $k-1$ 个仍未完成，共持有 $n(k-1)$ 个，再多 1 个即可使至少一人拿齐。所以充分的总量界限是 $m\ge n(k-1)+1$，即 $nk<m+n$。

这个结论回答的是不加安全检查时的最坏分配保证，不能说成银行家算法能够工作的必要条件。银行家可以主动推迟不安全请求，使资源较少的系统仍保持安全。例如两进程各最多需要 3 个、系统共 3 个，完全可以先满足一个，再满足另一个；最大需求之和 6 不满足 $6<3+2$，仍能安全运行。遇到题干把这两种问题混写时，应先明确要求的是任意分配保证，还是某个状态能否批准。

## 检测、解除和恢复 {#os-4-4}

检测允许系统运行到某种资源等待状态后，再判断是否已经死锁。单实例资源可以构造进程等待图；多实例资源要结合当前持有量、可用量和**当前未满足请求**进行化简。这里使用的 Request 是已经提出、正在等待的数量，不是未来最大 Need。

令 Work 为当前可用量。对当前请求能由 Work 满足的进程，假定其继续执行并释放已持资源，删除其相关分配与请求边，再寻找下一可化简进程。若有持有资源的进程最后仍无法化简，则该资源等待状态中存在死锁。没有占有任何资源的等待进程可能受死锁影响，却不一定属于维持资源环的核心；具体“死锁进程集合”的定义与检测初始化规则应一并说明。

例如 A、B 各 1 个，P 持 A 等 B，Q 持 B 等 A，Available 为 $(0,0)$，两人的当前请求分别为 $(0,1)$、$(1,0)$。任何人都无法化简。若第三个进程持有另一个 B 且能不等待地完成，则它归还后 P 可推进；这就是多实例有环却未必死锁的同一机制。

检测确认死锁后，可以终止全部死锁进程，或逐个选择牺牲者直到环被打破；也可在资源允许恢复时剥夺资源，并把受影响进程回滚到安全检查点。选择牺牲者需要考虑已完成工作、资源占用、恢复代价和优先级；每次都牺牲同一个低优先级进程，可能造成饥饿。仅降低某死锁进程优先级不会使它释放正持有的资源，不能单独解除等待环。

### 三类处理策略检查的不是同一件事

| 共同维度 | 预防 | 避免 | 检测与解除 |
| --- | --- | --- | --- |
| 何时作决定 | 事先规定请求、持有或分配规则 | 每次请求拟获批准时检查新状态 | 允许正常申请，定期或按事件检测当前状态 |
| 主要依据 | 资源是否可共享、能否剥夺、申请次序等 | 最大需求 Max、已分配量和当前可用量 | 当前分配、当前未满足请求 Request 和可用量 |
| 怎样处理有风险的请求 | 不符合规则便不能按该方式申请或持有 | 试分配后不安全则回滚并推迟 | 不以安全性为每次分配的必要条件，可能事后发现死锁 |
| 保证来自哪里 | 至少一个死锁必要条件被规则破坏 | 始终保留一个能覆盖全部进程的安全序列 | 检出以后终止、剥夺或回滚，释放维持等待环的资源 |
| 主要代价 | 申请受限、资源可能闲置 | 需要可信的最大需求，且有反复安全检查开销 | 需要检测及恢复，可能丢失已经完成的工作 |

两种“假定某进程完成并释放资源”的算法外形相似，输入却不同：银行家用未来可能达到的 Need 检查完成保证，检测用已经提出的 Request 判断当前等待能否解除。不能因为化简步骤相似，就把“不安全”直接改称“已死锁”。

## 自测：分别判断现在和最坏未来 {#os-4-review}

以下为原创回顾设问。

1. 资源分配图有环，是否立即判死锁？还缺什么信息？
2. 银行家安全检查中，一个进程可完成时，Work 应增加 Max、Need 还是 Allocation？
3. 新请求不超过 Need 且不超过 Available，能否直接批准？
4. 安全检查失败，能否立即宣布所有剩余进程已经死锁？
5. 3 个进程每人最多要 2 个同类资源，多少个资源可以在任意分配下保证不发生这种资源死锁？若只有 2 个，银行家是否一定无法运行？

### 自测答案

1. 要看资源实例数及可化简状态。相关类型均为单实例时环足以判定，多实例时还要检查能否由其他实例打破等待。
2. 增加 Allocation，假借出的 Need 在完成后归还，净效应抵消。
3. 不能，还要试分配并保持安全。
4. 不能，Need 是最大未来需求；实际当前 Request 可能更小或尚未提出。
5. $3(2-1)+1=4$ 个提供任意分配保证。只有 2 个仍可采用安全分配，先让一个拿齐、完成后轮到别人；资源总量界限不是银行家的必要条件。
